### RT-01 — Low — A capped keep mask cannot route around a component whose contract stops answering

**Defect.** Under the capped methodology, `IndexRule._snapshotMarket` prices every component, kept ones included,
because a kept component's market cap sits under every other component's weight (DA-06). `_price` read the token's own
`decimals()` live on every call. Take a component whose contract stops answering, the way a proxy does once its
implementation is withdrawn or broken; wSOL (a Wormhole BeaconProxy) and AAVE are the upgradeable launch components.
For such a component, the following all reverted on every capped index that held it:

- `startRebalance(keepMask)`, for the guardian and the owner as well as for strangers;
- `previewTarget`;
- `proposeConfig`, because `checkConfig` runs the same `_price`.

Delisting leaves the component in the index. Capped rebalancing therefore stayed frozen for as long as the token did,
possibly for good, while the docs promised that a keep mask routes around a component whose reads revert (DA-14).
DA-14's test used an uncapped index and a mock whose `decimals()` still answered, so it could not see this. No funds
were at risk: `redeemSkipping` and `claim` kept working, and an uncapped index with the same mask rebalanced normally.

**Fix.**
- `IndexFactory.executeListing` records the token's decimals (`tokenDecimals(token)`) when a config comes into force,
  reading them once more right after `checkConfig` has read and bounded them, and records them again at every config
  refresh. `_price` bounds the record again on every use, so a token that answered the two reads differently would
  fail closed above 18 decimals; below, it is a token outside the whitelist policy, which a live read never guarded
  against either, since it could change its answer at any time.
- `IndexRule._price` takes a `listed` flag. It prices a listed token with the recorded decimals, and only
  `checkConfig` reads the token live.

The rule now calls nothing on a listed token to price it, so a capped snapshot reads a kept component's feed and
nothing else. Feed decimals stay live, for the proxy-repoint reason the design rules give. A token whose contract
stops answering still takes no config change, since `checkConfig` reads it, but it needs none while its feed answers.
The ABI gains `IIndexFactory.tokenDecimals(address)`; nothing is removed or retyped. One behaviour moves the other
way: a token whose `decimals()` changes after listing, which only an upgradeable one can do, is priced at the recorded
decimals until a config refresh records the new ones, where a live read repriced it at once. The README's known
limitations say so, with the recourse; the same record stops a token's admin from repricing it through `decimals()`
before a snapshot.

**Design-rule change.** AGENTS.md said decimals are "never cached". That now holds for a feed's decimals only; a
token's are recorded at listing. The reasoning is in AGENTS.md: a standard ERC-20's decimals never change, and a live
read of the token is the one call a dead component can fail.

**Evidence.**
- `test_RT01_aCappedKeepMaskRoutesAroundAComponentThatNoLongerAnswers` in `test/IndexToken.rebalance.t.sol` is DA-14's
  capped twin. Its kept component reverts `balanceOf` and `decimals`, and the guardian starts and settles a capped
  rebalance around it.
- `test_RT01_RT19_aListedTokenIsPricedWithTheDecimalsRecordedAtListing` in `test/IndexRule.t.sol` checks the rest of the
  mechanism:
  - the record is written at listing;
  - a later change to the token's decimals is not read;
  - a config refresh records them again, when it is executed and not when it is proposed;
  - a delist keeps the record, so indexes that still hold the token still price it;
  - a refresh the rule refuses leaves the record in force.
- `test_RT01_everyPricingPathIgnoresTheTokenItself` in `test/IndexToken.rebalance.t.sol` holds the paths the capped
  start does not reach to the same answer once the token stops answering: `settlementValues` on a leg that moves,
  `navPerToken`, `weights` and `initialUnits`.
- `test_price_readsFeedDecimalsLive` replaces `test_price_readsDecimalsLive`, which changed only the token's decimals
  although its rationale was the feed's; the new test changes the feed's decimals instead, the half of that rationale
  that still holds, and the token half moved into the RT-01 test above.
- `MockPausableToken.setReadsBroken` now breaks every ERC-20 read (`name`, `symbol`, `decimals`, `totalSupply`,
  `balanceOf`, `allowance`), the way a withdrawn implementation does, and `test_pausableToken_brokenReadsFailEveryRead`
  covers it.
- Mutants, each run against the whole non-fork suite with `src/` restored byte for byte afterwards:
  - `_price` reading the token live again (`uint8 tokenDecimals = IERC20Metadata(token).decimals();`) fails both
    RT-01 rule and keep-mask tests, the keep-mask one with `reads broken` and the rule one on "the token itself is not
    read again";
  - `settlementValues`, `navPerToken` or `_market` alone passing `listed = false` fails
    `test_RT01_everyPricingPathIgnoresTheTokenItself` with `reads broken` (an independent review found these three
    surviving the first version of the tests, which is why that test exists);
  - recording at the proposal instead of at execution fails on "a config refresh records them again, at execution";
  - clearing the record on delist fails on "delisting keeps the record".
- The red team's own PoC, a real OpenZeppelin `BeaconProxy` whose beacon is upgraded to an implementation that reverts
  every call, passes on `70fda57` and fails against the fix.

### RT-02 — Info — During the auction the executor orders its fill ahead of a public exit or cancel

**Mechanism.** The fill can land in any block of the 24-hour auction, and whoever holds shares in that block pays its
haircut. An executor watching the mempool can therefore:
- put its fill ahead of a public `redeem`, which is then valued at the post-fill units;
- put it ahead of a guardian's `cancelRebalance`, which then has nothing left to cancel.

A mint is different, and not an ordering attack. Shares issued while a rebalance is pending share the haircut of any
fill that lands after them: the verifier measured the same loss with the fill right behind the mint and a block later,
and an independent review measured no loss at all with the fill ahead of the mint. Only the mint's timing matters.

The zap's `expectedNonce` makes a front-run burn revert, but only after the haircut has landed.

**What the numbers show.** On a $10.25M capped launch basket at a 0.904 multiplier, the front-run holder lost $17,529
of $5.13M. That is exactly what a holder who stayed through the fill lost. Nothing beyond the documented executor take
moves; what changes is that the exit meant to avoid it fails. ARCHITECTURE.md said holders "can leave in kind before it
settles", which holds only during the 2-day notice.

**Disposition.** DOCUMENTED. No change to the token can protect an exit, since a revert after the fill cannot undo it,
and issue and redeem must stay open. The following now say that the notice is the window to leave in, that exits and
cancels during the auction go through a private relay, and that a mint while a rebalance is pending shares the coming
haircut whatever the ordering, so the app warns before one:
- ARCHITECTURE.md ("Start above par, end below" and the rebalance flow);
- the README's rebalance steps, frontend notes and known limitations;
- AGENTS.md.

A zap-level opt-out of mints during a live auction was considered and left for a future zap. It would only protect a
mint, and the verifier showed a mint's loss does not depend on the fill's ordering.

**PoCs.** `econ-mev__ExitFrontRun.t.sol` (with `econ-mev__RedTeamBase.sol`) and `verify-2__ExitFrontRunCheck.t.sol`.

### RT-03 — Info — Whether a small index can settle depends on rounding, not on one whole token

**Defect.** AGENTS.md said "an index with less than one whole token outstanding cannot settle at all". Nothing in the
code uses one token as a threshold. What limits a small index is rounding: a growing leg is delivered in whole raw
units, rounded down, so when a growing leg comes to a few dozen raw units the rounding alone can cost more than the
2.5 points between the auction's 0.9 floor and the 0.875 ratio. On a basket with a WBTC-like component at the
recommended 10,000 raw units per token (verify-3's setup):

| Supply | at 12 h (1.2) | at 20 h (1.0) | last second (0.9) |
|---|---|---|---|
| 0.1 token | settles | settles | settles (ratio 0.899) |
| 0.01 token | settles | settles | refused (0.8725, WBTC in 23 raw units) |
| 0.001 token | settles | refused (0.759) | refused |
| 6e14 wei | refused | refused | refused |

An index whose growing legs all round to zero while a shrinking one releases something cannot settle at all; one so
small that no leg moves settles with nothing moved. The red team's first write-up, that 0.999, 0.01 and 0.001 tokens
settle and only a dust band around 1e12 wei fails, held only at the 1.2 multiplier its PoCs filled at; an independent
review of the documentation found the late-auction refusals, and the table above was measured against the fixed tree.

**Disposition.** DOCUMENTED. The design rule now describes the rounding limit. The same one-token sentence stands in
the DA-05 row of `audit/2026-09-19-triage.md` and is left there as that triage's record; this entry supersedes it.

**PoCs.** `second-wave__SubTokenSettle.t.sol` and `verify-3__SubTokenSettleSweep.t.sol`.

## RT-04 — Low — The turnover gate and a small holding far below its weight

**Defect.** `startRebalance` required `min(sold, bought) / activeValue >= MIN_TURNOVER` on the band-clipped step. The
band lets a growing component at most double, so a step buys at most that component's own holding. A basket whose
distance from its rule sits in a component held below 0.5% could therefore never start a rebalance, for a stranger,
the owner or the guardian, and under the uncapped methodology no price move helps, because holdings and weights both
scale with price. PoC path 1: after a DA-18 upward supply correction of wSOL, an index held 0.42% SOL against a rule of
4.10% and was refused for twelve months of price moves. Path 2: a creator's index with WBTC at 1/2000 of its rule
weight never converged. ARCHITECTURE section 3's convergence claim was false for these states.

**Fix.** `IndexRule.shortfall(tokens, units, methodology, keepMask)`, a new view, reports the distance to the rule
before the band: the value the rule wants moved out of the rebalanced components that hold more than their weight's
share and can still shrink. `startRebalance` refuses a step below MIN_TURNOVER only if it trades nothing or the
distance is below MIN_TURNOVER too, and computes the distance only in that case. `turnover` keeps its meaning, the
value traded, so DA-08's property holds and no existing test changed its expected value. One test was adjusted:
`test_DA22_CRI33` mocks the rule's turnover one wei under the threshold, and now also mocks the distance under it,
which keeps it on the traded turnover's own boundary. The ABI gains the view; nothing is removed or retyped. This
changes the design rule that states what MIN_TURNOVER measures (AGENTS.md, DA-08).

The independent review of the fix found that the first version, which measured the growing side, counted distance no
step can close: a component held at one raw unit has a floor of one raw unit, so an excess it holds kept the gate open
on every later drift, and a routine 0.4% supply refresh then let a stranger start a 0.1% step the gate exists to
refuse. Measured on the side that sells, over components the band can still shrink, the stuck unit drops out, and every
case the finding described measures the same.

**Evidence.** In `test/IndexToken.rebalance.t.sol`:
- `test_RT04_shortfallIsTheDistanceToTheRuleBeforeTheBand`: 40% against a 20% step, and a keep mask excludes the kept
  component;
- `test_RT04_shortfallRefusesMismatchedLengths`;
- `test_RT04_aBasketFarFromItsRuleStartsThoughEachStepIsSmall`: an index at 0.05% of a 60% component starts, settles
  and doubles again;
- `test_RT04_DA08_theDistanceGateAtItsEdges`: a zero step is refused however far the basket sits, and a one-wei step
  starts at a distance of exactly MIN_TURNOVER and not a wei under it;
- from the review, `test_RT04_aComponentStuckAtOneRawUnitDoesNotHoldTheGateOpen`,
  `test_RT04_aKeepMaskStartIsMeasuredOverTheRebalancedComponentsOnly`, `test_RT04_aCappedKeepMaskRenormalisesTheWeights`
  and `test_RT04_anUncappedKeptComponentWithAStaleFeedIsNotRead`.

Mutants, each against the whole non-fork suite, all killed: the old gate; the zero-step guard dropped; `<=` for `<` on
the distance; the growing-side measure; the stuck unit counted; the keep mask not passed to `shortfall`; `want`
computed over WAD instead of the active weight; and the snapshot inside `shortfall` ignoring the keep mask, which read
a kept stale feed and reverted.
